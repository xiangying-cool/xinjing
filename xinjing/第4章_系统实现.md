# 第 4 章 系统实现

## 4.1 系统实现总体说明

### 4.1.1 整体架构设计

"心镜"系统在工程上实现为由 **Web 全栈平台、AI 深度学习预测子模块、RAG 中间服务、语言模型服务和数字人表现层**共同组成的模块化原型，另有 VR 深评子系统作为扩展链路预留接入。整体数据流遵循"前端交互—后端编排—模型分析—结果反馈"的组织方式：用户经由 Web 平台完成基础信息录入、量表填写与初步交互；AI 深度学习预测模块在用户提交结构化信息后进行即时推理；当需要对结果进行解释或提供后续支持时，用户文本进入 RAG 中间层，经知识增强与风险路由后交给语言模型生成回复，最终由数字人表现层输出交互结果。

各服务监听端口如下表所示：

| 服务模块 | 技术框架 | 监听端口 | 职责边界 |
|---|---|---|---|
| Web 后端 API | FastAPI 0.115 | 8000 | 业务逻辑编排、ORM 持久化、JWT 认证 |
| RAG 中间服务 | FastAPI 0.115 | 8001 | 知识检索、风险路由、增强提示构造 |
| 数字人表现层 | aiohttp + aiortc | 8010 | WebRTC 媒体流、数字人渲染、LLM 调用 |
| Web 前端 | Vite 7 开发服务器 | 5173 | 用户界面、状态管理、媒体权限 |

系统整体依赖 Python 运行环境（Anaconda 3.12.3）、MySQL 8.0 数据库和 Node.js 工具链，各服务通过 HTTP 接口通信，前端通过 Vite 反向代理将 `/api`、`/livetalking` 等路径分别转发至对应后端端口，从而保证开发环境下各服务的统一访问入口，消除跨域问题。

### 4.1.2 架构设计原则

系统架构遵循以下核心设计原则：

**关注点分离（Separation of Concerns）**：Web 后端专注业务编排与持久化，RAG 服务专注知识检索与安全路由，数字人层专注媒体生成与实时传输，三者之间仅通过 HTTP 接口耦合，任一模块可独立替换或扩展。

**安全优先（Safety-First）**：心理健康领域的特殊性要求系统将用户安全置于最高优先级。危机响应路由在 RAG 层和数字人层均设置独立检测，构成多层防御，任一层触发高风险均立即终止 LLM 调用并输出固定危机回复，确保不因模型幻觉产生有害内容。

**降级容错（Graceful Degradation）**：各模态数据（人脸、语音、量表、文本）缺失时系统仍能基于可用模态输出推理结果；RAG 服务超时时自动降级为关键词危机检测 + 原始系统提示兜底，保证交互连续性。

## 4.2 Web 全栈平台实现

### 4.2.1 前端实现

Web 前端采用 **Vue 3.5 + Vite 7 + Tailwind CSS 3 + Vue Router 4** 技术栈实现，以 ECharts 6 承担数据可视化功能，以 `@vueuse/core` 提供组合式工具集。Vue 3 的组合式 API（Composition API）相较于 Options API 在逻辑复用和 TypeScript 推断上具有显著优势，配合 `<script setup>` 语法糖可将组件样板代码缩减约 40%。

#### 页面组件架构

页面按功能拆分为以下独立视图组件，各组件通过 Vue Router 4 的懒加载策略（`defineAsyncComponent` + 动态 `import()`）实现按需加载，减少首屏 JS 体积：

| 组件 | 核心功能 | 关键技术点 |
|---|---|---|
| **LoginPage** | 注册/登录，JWT 存储 | JWT 存储于 `localStorage['xinjing_auth']`，401 响应抛出错误并跳转 |
| **HomePage** | 系统首页，风险摘要 | 近期评估摘要聚合展示 |
| **ScreeningPage** | 辅助筛查主页面 | 量表选择、AI 预测表单、PHQ-9 Q9 阳性触发 SOS 预警 |
| **CompanionPage** | 数字人情绪陪伴 | WebRTC Offer-Answer 协商、对话管理、干预工具栏 |
| **MoodCalendarPage** | 情绪日历 | 月历打卡、日记记录、按月查询 |
| **ReportPage** | 历史评估报告 | report_json 结构化展示 |
| **AnalyticsPage** | 趋势分析 | ECharts 折线图、情绪快照时序展示 |
| **AboutPage** | 系统介绍 | 静态内容 |

#### 统一接口调用层

前端统一封装 `api.js` 接口调用层，所有请求携带 JWT Bearer 令牌，采用以下设计要点：

1. **令牌懒读取**：每次请求调用 `getToken()` 从 `localStorage` 中解析，不缓存至内存，确保登出后立即生效；
2. **错误中断语义**：401 响应时 `throw new Error('Unauthorized')` 而非静默返回 `undefined`，确保调用链在 `await` 处正确中断，上层 `try/catch` 可统一处理；
3. **204 特殊处理**：`if (res.status === 204) return null` 避免对无响应体的接口调用 `res.json()` 导致的 `SyntaxError`；
4. **错误信息透传**：非 2xx 响应时解析 FastAPI 标准错误结构 `{ detail: string }`，为用户提供后端具体错误描述而非通用 HTTP 状态文本。

#### WebRTC 接入设计

`CompanionPage` 通过以下精确流程完成 WebRTC 建连：

```
前端                                       LiveTalking 服务端 (8010)
  |                                               |
  |── createOffer ──→ 本地 SDP ──────────────────→|
  |                          ICE Gathering 完成后  |
  |←── answer SDP + sessionId ──────────────────|
  |── setRemoteDescription ──→                   |
  |                                               |
  |── POST /livetalking/human {text, sessionId} ─→|
  |                          TTS+Wav2Lip 异步处理  |
  |←── RTP视频/音频帧 (H.264/Opus) ──────────────|
```

关键实现细节：创建 `RTCPeerConnection` 时添加 video 和 audio 两路 `recvonly` Transceiver（而非 `addTrack`），仅接收不发送，降低延迟；ICE Gathering 完成后（监听 `icegatheringstatechange === "complete"`）再提交 Offer SDP，避免因 Trickle ICE 中途候选项变化导致协商失败；获取 `sessionId` 后缓存在组件状态中，后续每次发送消息均携带，确保服务端正确路由至对应 `HumanPlayer` 实例。

### 4.2.2 后端实现

后端采用 **FastAPI 0.115 + SQLAlchemy 2.0 ORM + Pydantic v2 + PyMySQL** 实现，以 `python-jose` 生成 HS256 JWT 令牌（默认有效期 120 分钟），以 `passlib[bcrypt]` 完成密码哈希存储。CORS 策略限制来源为前端开发端口（5173）与数字人服务端口（8010）。

#### 路由模块划分

后端按业务域拆分路由模块，各模块职责如下：

| 路由前缀 | 模块文件 | 核心职责 |
|---|---|---|
| `/api/v1/auth` | `auth.py` | 注册（bcrypt 哈希）、登录（密码验证）、HS256 JWT 签发 |
| `/api/v1/evaluations` | `evaluations.py` | 评估会话生命周期、量表提交与评分、SOS 预警写入 |
| `/api/v1/depression-predict` | `depression_predict.py` | AI 深度学习抑郁风险推理、报告持久化 |
| `/api/v1/chat` | `chat.py` | 聊天会话创建、消息记录、RAG 服务代理调用 |
| `/api/v1/mood-calendar` | `mood.py` | 月历查询、逐日打卡与日记记录、情绪趋势快照 |
| `/api/v1/reports` | `reports.py` | 历史报告分页查询、report_json 结构返回 |

#### 依赖注入体系

系统基于 FastAPI 的 `Depends()` 机制构建两层依赖：

- **数据库依赖**（`get_db`）：`yield` 模式确保请求结束后自动调用 `db.close()`，避免连接泄露；
- **认证依赖**（`get_current_user`）：从 `Authorization: Bearer <token>` 中解码 JWT，查询 `users` 表验证用户有效性；所有业务端点均通过 `current_user: User = Depends(get_current_user)` 注入，无需在每个函数内重复认证逻辑。

#### 量表评分架构

量表评分逻辑集中于 `services/scoring.py`，实现 PHQ-9、SDS（含 10 道反向计分题）、AIS 和 PSS 四套量表的分值计算与风险分级：

- **PHQ-9**：9 题 0–3 分，总分 0–27，阈值（5/10/15/20）对应无/轻/中/重度；第 9 题（`answer_values[8] > 0`，自杀意念）单独触发 `EmergencyAlert` 写入，实现量表层面的自动预警；
- **SDS**（Zung 抑郁自评量表）：20 题，其中 10 道为反向计分题（题目序号 2、5、6、11、12、14、16、17、18、20，即 0-indexed 集合 `{1, 4, 5, 10, 11, 13, 15, 16, 17, 19}`）；原始分乘以 1.25 取整得标准分，≥53 判为抑郁症状；
- **AIS**（Athens 失眠量表）：8 题，≥6 分为失眠；
- **PSS**（感知压力量表）：10 题含 4 道反向计分，≥27 为高压力。

#### 数据组织设计决策

**"元数据入库、实体外链"模式**：对音视频等大体积文件，`media_assets` 表仅保留路径、类型、大小和处理状态，媒体实体文件存储于本地文件系统。这一设计避免了数据库因 BLOB 存储膨胀影响查询效率，同时 URL 字段为后续迁移至对象存储（OSS/MinIO）预留了扩展路径。

**JSON 列策略**：`used_modalities`、`modality_weights`、`dimension_scores`、`report_json` 等字段采用 JSON 类型存储，在保持关系型数据库 ACID 特性的同时，为结构灵活的半结构化数据提供原生支持，避免了过度规范化带来的多表 JOIN 开销。

### 4.2.4 AI 深度学习预测模块实现

AI 深度学习预测功能以 FastAPI 端点 `POST /api/v1/depression-predict` 的形式对外提供服务，已完整实现并可在演示阶段使用。

#### 模型架构

系统采用两阶段推理管线：

**阶段一：特征预处理（scikit-learn ColumnTransformer）**

`scaler.pkl` 是基于训练集拟合的 `ColumnTransformer`，内部对连续型特征（`Age`、`Sleep_Duration`、`Work/Study_Hours`、`Financial_Stress`、`Study/job_Satisfaction`、`Academic/work_Pressure`）施加标准化变换（`StandardScaler`：$z = (x - \mu) / \sigma$），对二值特征列保持原值透传，最终输出固定维度的归一化特征矩阵。

**阶段二：神经网络推理（Keras Sequential）**

`keras_model.h5` 为 Keras Sequential 神经网络，接受标准化后的 11 维特征向量，经隐藏层非线性变换后，通过 Sigmoid 输出层输出区间 $[0,1]$ 内的抑郁风险概率 $\hat{p}$。

#### 输入特征（11 维，与 ColumnTransformer 精确对应）

| 特征字段（scaler `feature_names_in_` 精确列名） | 含义 | 类型 |
|---|---|---|
| `Age` | 年龄 | 连续值 |
| `Sleep_Duration` | 每日睡眠时长（小时） | 连续值 |
| `Work/Study_Hours` | 每日工作/学习时长（小时） | 连续值 |
| `Financial_Stress` | 经济压力（1–10） | 连续值 |
| `Study/job_Satisfaction` | 工作/学业满意度（1–10） | 连续值 |
| `Academic/work_Pressure` | 工作/学业压力（1–10） | 连续值 |
| `Working_Professional_or_Student_Working_Professional` | 身份（在职=1，学生=0） | 二值 |
| `Dietary_Habits_Moderate` | 饮食一般（0/1） | 二值 |
| `Dietary_Habits_Unhealthy` | 饮食不规律（0/1） | 二值 |
| `Have_you_ever_had_suicidal_thoughts_?_Yes` | 是否有过自杀念头（0/1） | 二值 |
| `Family_History_of_Mental_Illness_Yes` | 家族精神疾病史（0/1） | 二值 |

> **重要**：性别（Gender）不在模型特征集内，前端收集该字段仅用于档案记录，不参与推理，不可向 ColumnTransformer 传入该列，否则将因 `feature_names_in_` 不匹配报 `columns are missing` 错误。

#### 推理流程

1. 前端提交 11 个用户填写字段；
2. 后端 `_preprocess()` 将枚举字段编码为二值特征，按 scaler 期望的精确列名和顺序构建 `pd.DataFrame`；
3. `ColumnTransformer.transform()` 标准化处理，输出 $\mathbf{x}_{scaled} \in \mathbb{R}^{11}$；
4. Keras 模型前向推理，输出概率 $\hat{p} = \sigma(\mathbf{w}^T \mathbf{x}_{scaled} + b)$；
5. 决策阈值 $\hat{p} > 0.65$ 判定为"可能存在抑郁"；
6. 写入 `evaluation_sessions`（`screening_type="ai_predict"`）和 `reports` 表，生成 `intervention_recommendations`（优先级 1–3 的三条建议）；
7. 返回 `depressed`、`prediction`、`probability`（保留 4 位小数）、`motivation`、`report_id`。

#### 工程优化：单例模型加载

模型通过 `@lru_cache(maxsize=1)` 装饰器实现进程内单例加载：

```python
@lru_cache(maxsize=1)
def _load_models():
    import tensorflow as tf   # lazy import，启动时不引入 TF 开销
    scaler = joblib.load(ML_DIR / "scaler.pkl")
    keras_model = tf.keras.models.load_model(str(ML_DIR / "keras_model.h5"))
    return scaler, keras_model
```

`tensorflow` 的延迟导入（`import tensorflow as tf` 在函数体内）避免了服务启动时引入 TF 初始化开销（约 2–3 秒）。`lru_cache` 保证后续请求直接复用已加载的模型对象，消除重复 IO 和内存重分配。

## 4.3 VR 深评子系统实现（扩展链路）

### 4.3.1 VR 场景实现

VR 深评子系统作为系统扩展链路设计，基于 Unity 3D + SteamVR 平台实现，围绕医院问诊与公园步行两类任务构建标准化实验空间。场景中设置虚拟医生角色，引导用户在相对自然状态下完成行为表达，以降低传统诊室环境对用户心理状态的干扰。

在工程实现中，VR 场景重点解决三类问题：其一，虚拟任务流程与现实评估逻辑的对应，保证不同场景采集结果的可比性；其二，任务触发点与数据采集窗口的清晰对应，便于后续按事件片段切分数据；其三，渲染逻辑与采集逻辑的相互独立，避免交互脚本变动影响数据记录稳定性。系统将任务控制脚本、传感器读取脚本和数据写出脚本分模块实现，并通过统一时间戳完成后续对齐。

### 4.3.2 多模态采集实现

数据采集模块接入 Azure Kinect DK、Empatica E4 手环、麦克风和头显内置眼动组件等设备，各模态采集方式如下：

- **步态数据**：Azure Kinect DK 深度相机采集三维骨骼关键点（32 个关节，100 Hz），覆盖用户行走与移动过程；
- **生理数据**：E4 手环采集心率（BVP，64 Hz）、皮肤电（EDA，4 Hz）等生理信号；
- **音频数据**：胸前固定麦克风以 16 kHz/16-bit 实时录制，保证语音分析采样质量；
- **眼动数据**：VR 设备内置红外组件采集眼位、瞳孔直径、开合度和注视点（90 Hz）。

所有采集信号在本地以统一格式组织，进入时间同步与窗口切分流程。

### 4.3.3 数据通信实现

通信层将各模态封装为包含时间戳、设备标识、采样频率和原始值的统一消息结构，通过有线连接（Azure Kinect、麦克风）和蓝牙无线（E4 手环）相结合的方式低延迟送达本地计算平台，再交由缓存模块进行同步和窗口化切分，应对多设备采样频率不同、协议不同和局部短时丢包带来的对齐问题。

### 4.3.4 深评模型落地实现

抑郁辅助检测模块部署于本地主机，以数据通信层汇总的多模态数据作为输入，经数据预处理、单模态特征建模与提取、多模态特征融合，输出抑郁状态判定结果。步态模态集成基于多层次图神经网络的步态特征建模方法，提取空间拓扑和时间动态特征；多模态融合结合基于多尺度跨模态知识蒸馏的检测方法，在部分模态缺失条件下仍能输出相对稳定的预测结果。

## 4.4 数字人模块实现

### 4.4.1 RAG 服务实现

RAG 模块被实现为以 **FastAPI** 为框架的独立 HTTP 服务（端口 8001），对外暴露 `/v1/rag/retrieve`（纯检索）和 `/v1/rag/answer`（检索+提示构造）两个端点。

#### 核心技术组件选型

| 组件 | 选型 | 选型依据 |
|---|---|---|
| 嵌入模型 | `bge-small-zh-v1.5`（sentence-transformers 本地加载） | MTEB 中文语义检索榜单 Top 级别小模型，384 维向量，CPU 推理延迟约 15–30ms/query |
| 重排模型 | `bce-reranker-base_v1`（CrossEncoder，本地加载） | 网易有道开源跨编码器，中文段落相关性判断精度优于单塔模型约 5–8% |
| 向量索引 | FAISS `IndexFlatIP`（内积相似度） | 配合归一化向量等价余弦相似度计算，无需近似索引即可精确搜索，适合知识库规模（< 10 万片段） |
| 稀疏检索 | `rank-bm25` BM25Okapi | 经典词汇匹配，对专业术语（药物名、量表名）召回优于纯向量检索 |
| 中文分词 | `jieba`（`cut_for_search` 模式）+ 正则英文 token | `cut_for_search` 在细粒度分词基础上增加长词切分，提高召回率 |
| 结果融合 | 倒数排名融合（RRF，$k=60$） | 无需调参即可稳定融合异构排序列表，相比线性加权对分数尺度不敏感 |

#### 完整检索链路与数学原理

**Step 1：Query 规范化**

对输入文本去除首尾空白、截断超过 200 字符的过长查询，防止嵌入模型输入超长导致截断失真。

**Step 2：风险检测（优先执行，见 4.4.5 节）**

在任何检索操作前执行风险分级，高风险直接短路返回，不进入检索流程，确保危机响应零延迟。

**Step 3：密集检索（Dense Retrieval）**

嵌入模型将 query 编码为单位向量 $\mathbf{q} \in \mathbb{R}^{384}$（`normalize_embeddings=True`），FAISS IndexFlatIP 计算内积：

$$\text{sim}(\mathbf{q}, \mathbf{d}_i) = \mathbf{q}^T \mathbf{d}_i = \cos(\mathbf{q}, \mathbf{d}_i) \quad (\text{因两者均已 L2 归一化})$$

取 Top-$K_{dense}=20$ 候选片段。

**Step 4：稀疏检索（Sparse Retrieval）**

jieba `cut_for_search` 分词后，BM25Okapi 按以下公式计算相关性得分：

$$\text{BM25}(q, d) = \sum_{t \in q} \text{IDF}(t) \cdot \frac{f(t,d) \cdot (k_1+1)}{f(t,d) + k_1 \cdot \left(1-b+b\cdot\frac{|d|}{\text{avgdl}}\right)}$$

其中 $k_1=1.5$，$b=0.75$（BM25Okapi 默认参数），$f(t,d)$ 为词频，$|d|/\text{avgdl}$ 为文档长度归一化因子。取 Top-$K_{sparse}=20$ 候选。

**Step 5：RRF 分数融合**

对密集检索列表 $R_{dense}$ 和稀疏检索列表 $R_{sparse}$ 中的每个片段 $d$，计算融合分数：

$$\text{RRF}(d) = \frac{1}{k + r_{dense}(d)} + \frac{1}{k + r_{sparse}(d)}$$

其中 $k=60$（超参数，控制尾部排名的贡献衰减速率），$r_{dense}(d)$ 和 $r_{sparse}(d)$ 分别为片段 $d$ 在两个排序列表中的排名（从 1 开始，未出现则视为 $+\infty$，贡献为 0）。

在基础 RRF 分数上叠加优先级加权与类别偏好加分：

$$\text{score}(d) = \text{RRF}(d) + \text{priority}(d) \times 0.005 + \text{category\_boost}(d) \times 0.05$$

其中 `priority` 为知识块的人工标注优先级（高优先级知识如危机资源联系方式获得加分），`category_boost` 为类别匹配加分（query 语义与知识块所属类别高度相关时激活）。

**Step 6：交叉编码器重排（Cross-Encoder Reranking）**

取 RRF Top-12 作为重排候选池（`rerank_candidates=12`），BCE-reranker 对每个 `(query, passage)` 对进行全局注意力计算：

$$\text{rel}(q, d) = \text{CrossEncoder}([CLS] \, q \, [SEP] \, d \, [SEP])$$

重排后得分 $\text{final}(d) = \alpha \cdot \text{rel}(q,d) + (1-\alpha) \cdot \text{RRF}(d)$（其中 $\alpha$ 由配置控制），联合排序取 Top-6。

相比单阶段检索，两阶段"召回+重排"架构的优势在于：召回阶段用轻量级向量/BM25 保证候选覆盖，重排阶段用重量级 CrossEncoder 精化排序，在精度与延迟之间取得最佳平衡。CrossEncoder 对 `(q, d)` 联合编码可捕捉 query 与 passage 之间的细粒度语义交互，显著优于双塔模型（Bi-Encoder）的独立编码。

**Step 7：多样性打包（Diversity Packing）**

两轮扫描保证上下文多样性与字符预算：

- 第一轮：按得分从高到低，若加入当前片段后累计字符数不超过 `max_context_chars=2600`，且该片段的来源文档未超出多样性上限（每文档最多 2 片），则加入结果集；
- 第二轮：若第一轮片段数未达到 `final_top_k=6`，放宽文档多样性限制补充剩余名额；
- 最终返回不超过 6 个、总字符不超过 2600 字的高质量上下文片段集合。

**Step 8：构建 PromptBundle**

组装 `system_prompt`（含风险等级约束，见 4.4.4 节）和 `user_prompt`（含对话历史、检索片段、引用标注格式），连同 `latency_ms` 各阶段耗时统计一并返回给调用方。

#### 知识库组织

知识库以结构化 Markdown 文档集合组织，当前包含 5 个文件：

| 文件 | 主题 | 优先级策略 |
|---|---|---|
| `01_crisis_response.md` | 危机应对与热线资源 | 高优先级（紧急联系信息标注 `priority=3`） |
| `02_professional_help.md` | 专业帮助寻求 | 中高优先级（就医建议标注 `priority=2`） |
| `03_sleep_and_routine.md` | 睡眠与作息调节 | 普通优先级（`priority=1`） |
| `04_family_support.md` | 家属陪伴指南 | 普通优先级（`priority=1`） |
| `05_chatbot_limits.md` | 数字人能力边界说明 | 普通优先级（`priority=1`） |

知识块构建采用句子边界切分策略（`[。！？!?；;]` 正则匹配）：

- `chunk_size=420` 字符上限，保证每块信息密度适中，不超出 CrossEncoder `max_length=512` token 限制；
- `overlap=80` 字符重叠，通过将上一块末尾 80 字符拼接至下一块开头，解决跨块语义断裂问题；
- 每块计算 MD5 哈希作为 `chunk_id`，保证内容一致时 ID 稳定，支持增量更新时的去重检测。

索引文件（FAISS `.faiss`、BM25 `.pkl`、chunks JSON、meta JSON）存储于纯 ASCII 路径（`E:/xinjing_rag/`），以规避 FAISS C++ 底层库 `FileIOReader` 不支持 Windows 非 ASCII 路径的技术限制。

### 4.4.2 RAG 与主对话链路接入实现

在整体数字人链路中，文本输入直接进入 RAG 检索；语音输入先由 Edge TTS 完成语音合成驱动数字人口型（当前版本数字人主要处理文本输入，即用户输入文本→ LLM 生成→ TTS 合成→ Wav2Lip 驱动）。

RAG 返回风险判断、知识片段与增强提示后，LiveTalking 主框架（`llm.py`）执行三路路由决策：

```
RAG 返回结果
    │
    ├─ route == "crisis" 或 handoff_required == True
    │       └─→ 直接输出 fixed_reply（固定危机回复，不调用 LLM）
    │
    ├─ route == "normal"
    │       └─→ system_prompt + user_prompt → LLM 流式生成 → 逐句驱动数字人
    │
    └─ RAG 超时 / 连接失败（降级）
            └─→ 关键词危机检测兜底 → SAFETY_SYSTEM_PROMPT + 历史拼接 → LLM
```

LLM 支持两种后端，通过启动参数 `--llm_provider` 切换：
- **阿里云 DashScope**：`qwen-plus` 等，OpenAI 兼容接口（`https://dashscope.aliyuncs.com/compatible-mode/v1`），支持流式输出；
- **Ollama**：本地部署模型（如 `qwen2.5:3b`），零成本离线运行，适合演示和隐私敏感场景。

流式 token 到达后，`_emit_stream_text` 按标点（`[。！？…]`）切句，逐句调用 `nerfreal.put_msg_txt()` 推送给数字人渲染管线。**句级推送而非 token 级推送**的设计理由：Wav2Lip 基于整句音频生成口型序列，单 token 粒度推送会导致口型抖动和音频卡顿；句级推送在自然停顿处切分，既保证了流式感，又给 TTS 合成留出完整语义单元。

### 4.4.3 知识库构建与更新实现

知识库文档修改后，通过索引构建脚本（`scripts/rebuild_index.py`）重新完成以下流程：

1. **文档加载**：遍历 `KNOWLEDGE_DIR` 下所有 `.md` 文件，读取全文；
2. **切块**：句子边界切分，`chunk_size=420`，`overlap=80`，计算 MD5 `chunk_id`；
3. **向量化**：BGE-small-zh-v1.5 批量编码（`batch_size=32`），L2 归一化；
4. **FAISS 索引构建**：`IndexFlatIP`，将所有向量逐批添加（`index.add()`）；
5. **BM25 语料更新**：jieba 分词后构建 `BM25Okapi` 对象，序列化为 `.pkl`；
6. **存储写入**：`faiss.write_index()`、`pickle.dump()`、`json.dump()` 分别写出索引、语料和 chunks 元数据。

建议优先补充：症状边界说明、就医流程、心理咨询与精神科区别、家属陪伴建议和本地资源列表。明确排除：药物剂量、停药换药指导及任何危险行为的可操作细节。

### 4.4.4 回答精炼化实现

早期实现中，检索结果以较长原文形式整体送入 LLM，生成回答偏长、接近资料复述，不符合心理支持对话"共情优先、指引简洁"的原则。

针对此问题，系统在 `prompting.py` 中对系统提示设计了 7 条分层约束：

**通用约束（任意风险等级）：**

1. 你是"心镜"心理健康数字助手，不是心理咨询师，不能做诊断；
2. 先用 1–2 句话共情，再提供 2–4 条具体可执行建议；
3. 若建议来自知识库，用 `[1]`、`[2]` 格式引用来源编号；
4. 避免重复用户原话、避免复述知识库原文；
5. 语气温和、用词简洁，单次回答不超过 300 字；
6. 若问题超出能力范围，诚实说明并建议寻求专业帮助。

**高/中风险附加约束：**

7. 首要任务是鼓励用户联系身边可信任的人或拨打危机热线（12356/120/110），不得在危机状态下继续展开一般性心理教育。

上下文字符上限（`max_context_chars=2600`）限制送入 LLM 的知识片段总量，避免提示过长导致模型注意力分散。对话历史保留最近 6 轮（`history[-6:]`），在上下文连贯性与 token 消耗间取得平衡。

### 4.4.5 风险控制实现

RAG 层 `safety.py` 实现三级风险识别，所有检测在向 LLM 发送前完成，构成系统安全的第一道防线；后端量表评分层的 `emergency_alerts` 写入构成第二道防线，形成双层安全架构。

#### 高风险（`risk_level = "high"`，`route = "crisis"`，`handoff_required = True`）

触发条件（二者之一满足即触发）：

**条件 A：文本关键词检测**

正则检测明确自杀意图词汇：`自杀|轻生|结束生命|去死|不想活了|活不下去|想死`

若同时检测到计划性或行动性词汇：`今晚|现在|马上|遗书|跳楼|割腕|吃药|上吊|烧炭|服毒|刀片|安眠药`，额外标记 `plan_or_action=True`，在危机回复中增加更紧迫的行动指引。

**条件 B：量表状态注入**

若调用方传入 `user_state.suicide_item_score > 0`（即 PHQ-9 第 9 题得分 > 0，存在自杀意念），无论文本内容如何，直接判为高风险。

这一设计将 PHQ-9 的临床筛查结果引入实时对话安全判断，体现了量表评估与 AI 对话的深度联动：即使用户在后续对话中未再次提及危机词汇，系统仍保持高风险警戒状态。

高风险时直接返回固定危机回复（含远离危险物品、联系身边可信任的人、拨打 12356/120/110 的具体指引），**不调用 LLM**，避免生成模型产生不可控输出。

#### 中风险（`risk_level = "medium"`，`route = "normal"`）

触发条件（满足其一）：

**条件 A：被动死亡愿望词汇**

正则检测：`消失就好了|活着没意义|活着好累|不如死了算了|希望不要醒来`

**条件 B：严重绝望词汇**

正则检测：`绝望|撑不住了|崩溃了|没人帮我|彻底没办法了`

**条件 C：量表阈值注入**

`user_state.phq9_score >= 15`（PHQ-9 重度抑郁阈值），即使文本未触发关键词，也提升为中风险级别。

中风险路由至普通生成路径，但系统提示中已包含风险等级感知的第 7 条额外约束（优先建议寻求支持系统）。

#### 低风险（`risk_level = "low"`，`route = "normal"`）

未触发上述任何规则，进入标准 RAG 增强生成流程。

#### 双层安全架构

| 防线 | 位置 | 触发时机 | 动作 |
|---|---|---|---|
| 第一层 | RAG `safety.py`（对话层） | 每次对话消息处理前 | 高风险：返回 fixed_reply，不调用 LLM；中风险：增强 system prompt 约束 |
| 第二层 | 后端 `evaluations.py`（量表层） | PHQ-9 第 9 题得分 > 0 时 | 写入 `emergency_alerts` 表（`source_type="phq9_q9"`），供后台临床人员审查 |

### 4.4.6 数字人表现层接入实现

数字人表现层基于 **LiveTalking** 框架实现，核心组件如下：

| 组件 | 选型 | 说明 |
|---|---|---|
| 视频驱动模型 | Wav2Lip（`wav2lip.pth`，256×256） | 基于人脸关键点的端到端唇形同步模型，推理延迟约 80ms/帧 |
| 实时传输协议 | WebRTC（aiortc） | H.264 优先（硬件加速友好），VP8 备选，Opus 音频 |
| ICE 服务器 | `stun:stun.freeswitch.org:3478` | 公网 STUN 穿透，适合局域网演示环境 |
| TTS 引擎 | Edge TTS | 默认音色 `zh-CN-YunxiaNeural`，零成本、低延迟中文 TTS |
| HTTP 框架 | aiohttp | 异步 HTTP，与 aiortc 的 asyncio 事件循环无缝集成 |
| 跨域 | aiohttp-cors（允许所有来源） | 开发阶段允许前端跨域访问 |

**完整接入流程：**

1. 前端 `CompanionPage` 创建 `RTCPeerConnection`，添加 video/audio `recvonly` Transceiver；
2. `createOffer` 后等待 ICE Gathering 完成（`icegatheringstatechange === "complete"`），将完整本地 SDP 发送至 `/livetalking/offer`；
3. LiveTalking 服务端创建 `HumanPlayer`（含 VideoStreamTrack、AudioStreamTrack），返回 answer SDP 和 `sessionid`；
4. 前端 `setRemoteDescription(answer)` 完成协商，视频流写入 `<video>` 元素，音频流写入 `<audio>` 元素；
5. 用户发送消息时，前端向 `/livetalking/human` POST `{text, type: "chat", sessionid}`，触发 LLM 异步生成流程；
6. LLM 流式输出经 `_emit_stream_text` 按句切分，推入 `nerfreal.put_msg_txt()` 队列；
7. 渲染管线异步消费队列：文本→ Edge TTS 合成音频 → Wav2Lip 生成唇形同步帧 → RTP 推流至前端。

Avatar 帧数据（`my_avatar`，242 帧静默视频）在服务启动时通过 `warm_up` 预热加载，保证首帧响应速度并避免首次请求的冷启动延迟。


### 4.5.2 关键部署注意事项

1. **RAG 索引存储路径必须为纯 ASCII**：FAISS C++ 底层 `FileIOReader` 在 Windows 上不支持含中文字符的路径，索引文件须存放于如 `E:/xinjing_rag/` 的纯英文路径，并在 `depression_rag_module/.env` 中相应配置 `STORAGE_DIR=E:/xinjing_rag`；

2. **嵌入与重排模型设备**：演示环境若无 CUDA，须在 `.env` 中将 `EMBEDDING_DEVICE=cpu` 和 `RERANK_DEVICE=cpu`；CPU 推理下 BGE-small-zh-v1.5 嵌入耗时约 15–30ms/query，BCE-reranker 重排耗时约 50–100ms/12候选，整体检索链路约 200–400ms；

3. **数据库初始化**：首次部署需执行 `Xinjing_test.sql` 建表，并在 `xinjing-backend/.env.test` 中填写正确的 MySQL 连接字符串（`DATABASE_URL=mysql+pymysql://user:pass@localhost/dbname`）；

4. **LLM API Key**：数字人对话依赖 DashScope（`qwen-plus`）或 Ollama 本地模型，DashScope 模式需配置环境变量 `DASHSCOPE_API_KEY`；

5. **TensorFlow 依赖**：AI 深度学习预测端点需要 TensorFlow ≥ 2.16（Python 3.12 兼容版本），Anaconda 环境中安装命令：`pip install "tensorflow>=2.16"`。

## 4.6 实现过程中遇到的困难与解决方法

### （1）AI 预测模型特征列名不一致导致 503

**问题根源**：后端 `_preprocess()` 函数最初使用了与模型训练时不同的 DataFrame 列名（如 `Work_Pressure`、`Job_Satisfaction`、`Work_or_Study_Hours`），且额外传入了模型并不包含的 `Gender_Male` 特征（该特征在训练时被剔除，模型特征集共 11 维，不含性别）。ColumnTransformer 的 `transform()` 方法在执行时校验输入 DataFrame 的列名集合与训练时 `feature_names_in_` 严格一致，列名不匹配或存在多余列均报 `ValueError: columns are missing`，被 `try/except` 包装为 `RuntimeError`，最终以 503 Service Unavailable 返回前端。

**诊断过程**：通过 `pickle.load()` 加载 `scaler.pkl` 并调用 `scaler.feature_names_in_.tolist()` 直接读取训练时的精确列名列表，发现实际列名含斜杠（`Work/Study_Hours`、`Study/job_Satisfaction`、`Academic/work_Pressure`），与代码中的下划线命名完全不符。

**解决方法**：逆向查询 scaler 的 `feature_names_in_` 属性，确认全部 11 个特征的精确列名，修正 `_preprocess()` 中的字典键名，同时移除不在模型特征集内的 `Gender_Male`。此外，删除 `app/api/` 目录下的 `.pyc` 字节码缓存文件并硬重启 uvicorn，确保 Python 解释器加载修改后的源文件而非旧的字节码缓存。

### （2）FAISS C++ 底层不支持 Windows 非 ASCII 路径

**问题根源**：FAISS Python 绑定底层为 C++ 实现，`faiss.read_index()` 最终调用 C++ `FileIOReader`，其内部使用 `fopen()` 系统调用。在 Windows 系统上，当路径包含中文字符（如项目目录名 `止计算机设计大赛`）时，`fopen()` 因 ANSI 编码与文件系统实际编码（UTF-8/GBK）不一致，抛出 `RuntimeError: Error reading index`，导致 RAG 服务启动失败。

**解决方法**：将索引存储目录迁移至纯 ASCII 路径（`E:/xinjing_rag/`），在 `depression_rag_module/.env` 中更新 `STORAGE_DIR=E:/xinjing_rag`，知识库文档和模型文件路径因 Python `pathlib.Path` 对 Unicode 路径支持良好，无需迁移。

### （3）TensorFlow 未安装导致预测端点持续 503

**问题根源**：运行环境（Anaconda base）缺少 TensorFlow，AI 预测端点的 `_load_models()` 在 `import tensorflow as tf` 时抛出 `ModuleNotFoundError: No module named 'tensorflow'`。由于 `_load_models()` 被 `@lru_cache(maxsize=1)` 修饰，首次调用失败后缓存的是 `RuntimeError` 异常而非模型对象，导致后续所有请求均直接报错，无法通过重试恢复。

**解决方法**：在 Anaconda 环境中安装 `tensorflow>=2.16`（Python 3.12 要求该版本以上），安装完成后需重启 uvicorn 进程（`lru_cache` 存储在进程内存中，重启后自动清除失败缓存，允许重新加载模型）。

### （4）RAG 模块 `.env` 路径硬编码为旧机器绝对路径

**问题根源**：开发环境迁移后，`.env` 文件中的知识库路径（`KNOWLEDGE_DIR`）、模型路径（`EMBEDDING_MODEL`、`RERANK_MODEL`）和存储路径（`STORAGE_DIR`）均保留了旧机器的 `d:/digitalpeople/...` 绝对路径，新机器上路径不存在，服务启动时批量报 `FileNotFoundError`。同时，`EMBEDDING_DEVICE=cuda` 和 `RERANK_DEVICE=cuda` 在无 GPU 的演示环境中导致模型加载失败。

**解决方法**：将所有路径更新为当前机器实际目录（`e:/止计算机设计大赛/计算机设计大赛/depression_rag_module/...`），将设备配置改为 `cpu`。鉴于 FAISS ASCII 路径限制，`STORAGE_DIR` 单独配置为 `E:/xinjing_rag/`（纯 ASCII 路径）。

### （5）数字人回答冗长、接近资料复述

**问题根源**：早期实现中，检索到的知识片段以原始 Markdown 格式整体送入 LLM 上下文，系统提示仅有简单的"请用中文回答"约束。LLM（尤其是 `qwen-plus`）在大量参考资料存在时，倾向于综合复述而非精炼提取，导致单次回答超过 500 字，缺乏共情开场和条目化结构，不符合心理支持对话的交互习惯。

**解决方法**：在 `prompting.py` 中重新设计 7 条分层系统提示约束（先共情、再 2–4 条建议、再转介提示，风险等级联动第 7 条约束），将上下文字符上限从无限制收缩至 2600 字符，对话历史保留最近 6 轮。改动后回答长度降至 150–250 字，引用标注（`[1][2]`）使回答可溯源，显著改善输出自然性。

### （6）PHQ-9 第 9 题（自杀意念）阳性未联动 RAG 风险检测

**问题根源**：原始实现中，PHQ-9 第 9 题阳性仅触发数据库 `emergency_alerts` 写入，未向 RAG 风险检测传递用户的量表状态。当用户在完成量表后进入数字人陪伴对话时，若文本中未再次出现危机关键词，RAG 的 `detect_risk()` 只基于文本模式，仍会走普通生成路由，存在对已识别高风险用户的防护缺口。

**解决方法**：在 RAG `QueryRequest` schema（`schemas.py`）中增加 `user_state: UserState` 参数，`UserState` 包含 `suicide_item_score`（PHQ-9 第 9 题得分）和 `phq9_score`（PHQ-9 总分）；`detect_risk()` 函数同时检测文本模式和 `user_state` 字段，确保量表结果维度的风险状态在整个对话生命周期内持续有效。后端 `chat.py` 在调用 RAG 服务时从数据库查询最近评估会话的量表结果，填充 `user_state` 参数。

## 4.7 本章小结

本章从工程实现角度对系统各模块的落地过程进行了系统说明。系统已完成以下核心模块的工程闭环：

- **Web 全栈平台**：Vue 3 + FastAPI + MySQL，JWT 认证体系，6 个业务路由模块，15 张数据库表覆盖用户、评估、量表、报告和陪伴全业务域；
- **AI 深度学习预测子模块**：Keras Sequential 神经网络 + scikit-learn ColumnTransformer，11 维精确特征集，`@lru_cache` 单例加载优化，端到端可用；
- **RAG 中间服务**：BGE-small-zh-v1.5 密集检索 + BM25Okapi 稀疏检索 + RRF 融合 + BCE-reranker 重排 + 多样性打包，三级风险路由（PHQ-9 量表状态与文本关键词双源联动），句级流式输出；
- **数字人表现层**：LiveTalking + Wav2Lip + WebRTC（H.264/Opus）+ Edge TTS + DashScope/Ollama LLM，支持实时唇形同步与流式对话；
- **双层安全架构**：RAG 层文本+量表双维度风险检测（第一防线）+ 量表评分层 `emergency_alerts` 自动写入（第二防线），危机场景绕过 LLM 直接输出固定回复。

VR 深评子系统作为扩展链路设计，已规划接口边界，待硬件环境就绪后可平滑接入。整体实现已具备完整的工程闭环和良好的扩展基础，可为后续测试分析与系统优化提供稳定支撑。
